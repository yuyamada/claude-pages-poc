# claude-pages-poc

PoC: publish content generated by [Claude Code Action](https://github.com/anthropics/claude-code-action) to GitHub Pages.

## How it works

`main` holds only the workflow and this README. All generated content and
the Hugo site config live on a separate `pages` branch, so automated
commits never touch `main` and never need rebasing against your own work.

1. Trigger the `Generate and Deploy to Pages` workflow manually (Actions tab → Run workflow, or `gh workflow run`).
2. The `generate` job checks out the `pages` branch (not `main`).
3. A shell step computes the current UTC timestamp (compact form for the filename, RFC3339 for front matter).
4. Claude Code Action runs in automation mode and writes a new dated report to `content/<timestamp>.md`, a plain Markdown file with `title`/`date` front matter. It only ever writes that one file — this is the only thing this workflow commits back to git, kept as Markdown because it's readable and diffable in a way generated HTML isn't.
5. [Hugo](https://gohugo.io) builds the site (`hugo --minify --destination _site`). `_site/` is a build output, gitignored, and never committed — it's fully derived from the committed Markdown every run.
   - Hugo's default Markdown renderer (Goldmark) has raw HTML passthrough **disabled by default** (`markup.goldmark.renderer.unsafe: false`), unlike most CommonMark-compliant renderers (pandoc, kramdown, pulldown-cmark) which pass raw HTML through unless explicitly told not to. This matters because an LLM-authored `<script>` tag would otherwise run in visitors' browsers with no review step in this pipeline.
   - `layouts/index.html` renders a paginated list of reports (title, formatted date, plain-text preview via `.Plain | truncate`) using Hugo's built-in `.Paginate` and page collections, instead of a hand-rolled bash listing. Page size is set via `[pagination] pagerSize` in `hugo.toml`.
6. Another shell step commits and pushes the new `content/*.md` file to `pages`, so report history persists across runs.
7. `actions/upload-pages-artifact` uploads `_site/` (the full built site), and the `deploy` job publishes it via `actions/deploy-pages`.

### Charts

Claude may optionally include one chart per report as a fenced code block
labeled `chart`, containing only a JSON object shaped like a Chart.js
config (`type`, `data`, `options` — no JavaScript). A Hugo render hook
(`layouts/_markup/render-codeblock-chart.html`) turns that code block into
a bare `<canvas data-chart="...">` element and sets a page-scoped flag;
`layouts/_default/single.html` checks that flag and appends one fixed,
human-authored `<script>` block (Chart.js from a CDN + a few lines that
call `new Chart(el, JSON.parse(...))`) only if a chart was found. Claude
never writes or controls any executable JavaScript — only the chart's
data.

Pages is configured with `build_type: workflow` (Settings → Pages → Build and deployment → Source: GitHub Actions), which deploys whatever `deploy-pages` is given regardless of branch — the `pages` branch here is purely a storage mechanism for the workflow's own state, unrelated to how Pages picks up content.

## One-time setup

- Repository secret `CLAUDE_CODE_OAUTH_TOKEN` must be set (Settings → Secrets and variables → Actions). Generate it locally with `claude setup-token` (requires a Pro/Max/Team/Enterprise subscription).
- Pages source must be set to "GitHub Actions" (Settings → Pages → Build and deployment).
- A `pages` branch must exist, with `hugo.toml` and `layouts/` already in place, before the workflow's first run, since `actions/checkout` fails on a ref that doesn't exist yet.

## Note

The workflow trigger is `workflow_dispatch`. Official Claude Code Action documentation is inconsistent about whether this event is fully supported yet ([one doc says "coming soon"](https://github.com/anthropics/claude-code-action/blob/main/docs/custom-automations.md)); this repo is partly to verify that in practice. If it doesn't work, the fallback is a `repository_dispatch` trigger fired via the GitHub API.
